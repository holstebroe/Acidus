# TB-303 Emulation — Parameter Confidence Table

This document cross-references the actual constants used in `src/core/` (`Oscillator`, `Filter`, `Envelope`, `SynthEngine`) against `TB303_RESEARCH_COMPENDIUM.md`. It answers two questions: **which numbers in the code are close to documented/measured hardware values (safe to trust), and which are tuned-by-feel placeholders (worth experimenting with until the "Faithful" engine matches a real 303)?**

Confidence levels:

- 🟢 **Confirmed** — matches a factory-service-notes value or a primary circuit analysis directly.
- 🟡 **Estimate** — a plausible value, order-of-magnitude or mechanism confirmed, exact number not independently sourced.
- 🔴 **Unsourced / free parameter** — no source found; treat as a pure calibration knob.

Both the "Accurate" and "Faithful" engines share the oscillator (`Oscillator.cpp`) and the CV-summing stage (`SynthEngine.cpp`); they differ only in the filter core (`Filter::processAccurateSample` vs `Filter::processFaithfulSample`). Where a row applies to only one filter mode, it's noted in the Notes column.

## Summary: what's most trustworthy vs. most worth experimenting with

**High confidence — leave alone unless a reference recording disagrees:**
- Slide time constant (60 ms)
- A=110 Hz / 4:1 octave VCO calibration
- Accent Sweep RC (47 ms) and Accent→VCA RC (1.55 ms) time constants
- Square duty-cycle endpoints (45%→70%)
- Accent-VCA-as-control-current-summation (not fixed dB) — already implemented correctly
- Dual-gang Resonance → Accent Sweep coupling (mechanism, not exact blend weight)

**Biggest opportunities to improve accuracy (in priority order):**
1. ~~**Feedback HPF frequency**~~ — **Fixed 2026-09.** `Filter::processFaithfulSample` now uses a 2-pole ~9 Hz (plausible range 5–15 Hz) coupling-pole network inside the resonance feedback loop, replacing the old 150→250 Hz sweep. `Filter::processAccurateSample` intentionally keeps the old approximation, since it's a separately-calibrated, already-liked-sounding mode. Verified stable (no NaN/Inf, no runaway levels) across max-resonance/cutoff/envMod/accent stress combinations; the resulting resonant-peak behavior at typical bassline cutoffs (150–800 Hz) should now be substantially stronger than before, since far less of the ladder's own output is stripped out of the feedback path before it can resonate.
2. **Widen the coupling-pole network further** (Faithful mode): currently 2 of the documented ≈6 poles are modeled explicitly inside the resonance loop (plus 1 input-side, 1 output-side = 4 total). Cheap to extend (each extra one-pole stage costs ~2 FLOPs per oversample tick — negligible for a mono synth), but there's no sourced target for where additional poles should sit, so this is a lower-priority, exploratory follow-up rather than a known fix.
3. **Square-only 150 Hz HPF in the oscillator**: research says this coloration isn't square-specific and isn't at 150 Hz — it's a shared saw/square coupling effect around 80–115 Hz that tracks pitch. Out of scope for the filter-focused update above (lives in `Oscillator.cpp`, not `Filter.cpp`); worth revisiting both the scope (apply to saw too, or move it into a shared post-selector coupling stage) and the frequency in a future pass.
4. **Resonance→cutoff 15% CV bleed** in `SynthEngine.cpp`: not corroborated by any source at all. Worth an A/B listening test with it disabled — it may be masking or duplicating the (also present) Accent-Sweep/Resonance-gang interaction.
5. **Saw 14 kHz LPF + quadratic bend, and the general shape of the oscillator waveshaper**: unsourced but low-risk to leave as-is (cheap, plausible-sounding, not contradicted — just not confirmed).

## Important parameter values that are **not emulated at all**

These are documented hardware behaviors (confirmed or reasonably well-supported by the research) with **no corresponding code** in this project. (Sequencer clock/gate/slide timing is intentionally excluded from this list: this project only emulates the sound engine, not the step sequencer — a host/DAW is responsible for note/gate timing.)

1. **6-bit pitch DAC quantization.** The real hardware pitch CV is generated by a 6-bit DAC (≈83 mV/semitone-class resolution before the ±3 mV trim tolerance). The oscillator here uses full double-precision floating point, i.e. effectively infinite pitch resolution — a strictly "smoother" instrument than the original in this one respect.
2. **Component-level variation and calibration drift.** `TB303_EMULATION_REFERENCE.md` §49 explicitly recommends small, slow per-instance variation in transistor Vbe/beta, capacitor value/leakage, resistor tolerance, and trim-pot settings for realism. None of this is implemented — every parameter is deterministic and identical run to run.
3. **Temperature drift** (§50) and **analogue noise floor** (§51). Neither is implemented; the signal path is fully deterministic and noiseless.
4. **A measured/derived BA662-style transconductance curve.** The VCA is `signal × envelope`, boosted by the accent control-current term, then passed through an asymmetric `tanh`. This gets the qualitative shape right (soft ceiling, not a hard linear multiply) but doesn't model an actual current-controlled-transconductance curve derived from the V662A reissue datasheet (§10 of the compendium).
5. **The dedicated Env Mod bias transistor (Q9) shifting the filter's DC operating point**, distinct from simply adding a CV term. The current implementation approximates this as an additive `cv_offset`/`cv_envmod` term in the same octave-CV sum as everything else, which gets the *qualitative* "small knob movement, big audible sweep" behavior in the right ballpark but doesn't model a literal bias-point shift interacting with the ladder's own nonlinear transfer curve.
6. **Resonance-dependent Accent Sweep time constant.** The real circuit's effective RC time constant for the accent-sweep capacitor varies continuously with the Resonance knob (via the 100 kΩ second-gang resistance) — the code uses one fixed 47 ms time constant for the capacitor regardless of Resonance, and instead expresses the Resonance/Accent-Sweep interaction entirely through a separate output-mixing weight (`resNorm * 0.7f` in `SynthEngine.cpp`). This is a reasonable approximation of the *result* but not the *mechanism*.
7. **Diode/transistor Vf asymmetry inside the filter.** The factory parts list includes at least one **germanium** diode (1S-188FM, Vf ≈ 0.3 V) alongside several **silicon** diode/transistor types (Vf ≈ 0.6 V), implying non-uniform forward-voltage behavior somewhere in the signal path. The filter's nonlinearity uses one uniform `Vt`/`tanh` shape for all four ladder stages, the new resonance-loop coupling-pole network, and the feedback path; no per-stage or per-junction Vf asymmetry is modeled. This would be cheap to add (a per-stage Vt multiplier) but there's no source for which stage(s) would use the germanium diode's lower Vf, so it's speculative rather than a known fix — flagged here as a "substantial guess" the user should treat with more skepticism than the coupling-pole frequency fix above.
8. **The remaining ≈2 of the documented ≈6 resonance-loop coupling poles.** See the Filter table above — 2 of an order-of-magnitude ≈6 are now modeled explicitly (plus 1 input-side, 1 output-side pole). Cheap to extend further but with no sourced target frequencies to aim for.
9. **Output/mixer coupling stage and stated output impedances** (10 kΩ line out, 8–30 Ω headphone out). Not relevant to a plugin's internal signal path, but worth noting as explicitly out of scope rather than accidentally omitted.
10. **Factory calibration-mode targets** (TM1–TM6 trim checkpoints, §11 of the compendium). There's no software "calibration mode" that could be validated against these checkpoints (e.g. exposing internal `vco_scale`/`filter_bias`-style hidden parameters, as the older reference doc's §53 recommends). All current parameters are the seven front-panel controls only.

## Performance note (2026-09 filter update)

All of the changes above are one-pole (or cascaded one-pole) linear filter stages evaluated once per oversampled tick inside `processFaithfulSample` — each costs roughly 2–4 FLOPs. At 8× oversampling and a typical host block/sample rate, this is immeasurably small next to the existing Newton-Raphson solve (3 iterations × a 4×4 tridiagonal solve, per oversampled tick) that already dominates the filter's cost. Since this is a monophonic synth (one filter instance active at a time, not one per voice in a polyphonic pool), there is substantial CPU headroom — none of the changes made here, nor the "cheap to extend further" follow-ups noted above (more coupling-pole stages, higher pole counts), are meaningful performance risks. The one change flagged above as **not** cheap is folding the coupling-pole network into the *implicit* Newton-Raphson solve itself (rather than treating it explicitly/pre-linearized, as done here) — that would enlarge the tridiagonal Jacobian to a pentadiagonal (or larger) system each Newton iteration, a real architectural change. It was deliberately not done: the coupling-pole's time constant (~17.7 ms at 9 Hz) is roughly 4 orders of magnitude longer than one oversampled step (~2.8 μs at 8×/44.1kHz), so treating it explicitly costs negligible accuracy — there's no numerical-quality reason to pay for the implicit version.
