# TB-303 Emulation — Parameter Confidence Table

This document cross-references the actual constants used in `src/core/` (`Oscillator`, `Filter`, `Envelope`, `SynthEngine`) against `TB303_RESEARCH_COMPENDIUM.md`. It answers two questions: **which numbers in the code are close to documented/measured hardware values (safe to trust), and which are tuned-by-feel placeholders (worth experimenting with until the "Faithful" engine matches a real 303)?**

Confidence levels:

- 🟢 **Confirmed** — matches a factory-service-notes value or a primary circuit analysis directly.
- 🟡 **Estimate** — a plausible value, order-of-magnitude or mechanism confirmed, exact number not independently sourced.
- 🔴 **Unsourced / free parameter** — no source found; treat as a pure calibration knob.

Both the "Accurate" and "Faithful" engines share the oscillator (`Oscillator.cpp`) and the CV-summing stage (`SynthEngine.cpp`); they differ only in the filter core (`Filter::processAccurateSample` vs `Filter::processFaithfulSample`). Where a row applies to only one filter mode, it's noted in the Notes column.

> **2026-09 regression & correction.** A first pass at two "biggest opportunities" below (the filter's resonance coupling-pole corner, and the oscillator's coupling HPF) turned out to be badly wrong in practice, based on over-reading two thin secondary-source summaries without being able to listen to the result. Both were reverted after direct A/B comparison against **RobinSchmidt/Open303** (`github.com/RobinSchmidt/Open303`, `Source/DSPCode/rosic_Open303.cpp`/`rosic_TeeBeeFilter.h`), a well-regarded, independently ear/measurement-tuned open-source TB-303 emulation that ships its own version of both stages with concrete numbers. Where this document cites an Open303 value below, treat it as meaningfully more trustworthy than an unverified "best guess" (though still not a factory-documented spec) — it's a second, working implementation's real, shipped constant, not just another guess.

## Summary: what's most trustworthy vs. most worth experimenting with

**High confidence — leave alone unless a reference recording disagrees:**
- Slide time constant (60 ms)
- A=110 Hz / 4:1 octave VCO calibration
- Accent Sweep RC (47 ms) and Accent→VCA RC (1.55 ms) time constants
- Square duty-cycle endpoints (45%→70%)
- Accent-VCA-as-control-current-summation (not fixed dB) — already implemented correctly
- Dual-gang Resonance → Accent Sweep coupling (mechanism, not exact blend weight)

**Biggest opportunities to improve accuracy (in priority order):**
1. ~~**Feedback HPF frequency**~~ — **Attempted 2026-09, caused a regression, reverted 2026-09.** See the Faithful-mode filter table above for the full history. `Filter::processFaithfulSample` is back to a single one-pole HPF anchored at 150 Hz (+ up to 100 Hz with Resonance), cross-validated against RobinSchmidt/Open303's shipped 150 Hz value. `Filter::processAccurateSample` was never touched (frozen, already-liked-sounding mode).
2. ~~**Square-only 150 Hz HPF in the oscillator**~~ — **Attempted 2026-09, caused a regression (worse than #1 — it hit both engine modes), reverted 2026-09.** See the Oscillator table above. `Oscillator::processNextSample` is back to a single, fixed (non-pitch-tracking) coupling HPF at ~44.5 Hz, cross-validated against Open303's shipped 44.486 Hz "pre-filter highpass" value.
3. **Add Open303-style low-frequency notch/allpass stages** *outside* the resonance feedback loop (Faithful mode): Open303 uses a ~7.5 Hz notch (bandwidth ~4.7) and a ~14 Hz allpass in series with the signal, separate from its feedback-loop highpass. This is a plausible, concretely-templated way to actually deliver on the "6 further poles" research claim without repeating the 2026-09 mistake of putting a low-frequency pole inside the resonance loop's gain path. Not attempted this round — flagged as the most promising next step, to be added and tested carefully (ideally with real listening, not just stability tests) rather than in the same pass as this regression fix.
4. **Resonance→cutoff 15% CV bleed** in `SynthEngine.cpp`: not corroborated by any source at all. Exposed as a CLAP parameter (`Res->Cutoff Bleed`, range 0–30%, default 15%) — worth an A/B listening test with it set to 0% to check whether it's doing anything useful versus the (also present) Accent-Sweep/Resonance-gang interaction.
5. **Saw 14 kHz LPF + quadratic bend, and the general shape of the oscillator waveshaper**: unsourced but low-risk to leave as-is (cheap, plausible-sounding, not contradicted — just not confirmed). Not exposed as a CLAP parameter this round.

**A cautionary note on this whole document's methodology:** items 1 and 2 above are a concrete example of the risk described at the top of this file — a plausible-sounding correction, derived from secondary-source text without the ability to listen to the result, made the emulation sound *less* like a TB-303, not more. Where a well-regarded reference implementation's actual shipped value is available (as it was here, via Open303), prefer it over a textual secondary-source claim, and treat any further from-scratch "correction" attempt with real caution until it's been validated by ear against a reference recording.

## Important parameter values that are **not emulated at all**

These are documented hardware behaviors (confirmed or reasonably well-supported by the research) with **no corresponding code** in this project. (Sequencer clock/gate/slide timing is intentionally excluded from this list: this project only emulates the sound engine, not the step sequencer — a host/DAW is responsible for note/gate timing.)

1. **6-bit pitch DAC quantization.** The real hardware pitch CV is generated by a 6-bit DAC (≈83 mV/semitone-class resolution before the ±3 mV trim tolerance). The oscillator here uses full double-precision floating point, i.e. effectively infinite pitch resolution — a strictly "smoother" instrument than the original in this one respect.
2. **Component-level variation and calibration drift.** `TB303_EMULATION_REFERENCE.md` §49 explicitly recommends small, slow per-instance variation in transistor Vbe/beta, capacitor value/leakage, resistor tolerance, and trim-pot settings for realism. None of this is implemented — every parameter is deterministic and identical run to run.
3. **Temperature drift** (§50) and **analogue noise floor** (§51). Neither is implemented; the signal path is fully deterministic and noiseless.
4. **A measured/derived BA662-style transconductance curve.** The VCA is `signal × envelope`, boosted by the accent control-current term, then passed through an asymmetric `tanh`. This gets the qualitative shape right (soft ceiling, not a hard linear multiply) but doesn't model an actual current-controlled-transconductance curve derived from the V662A reissue datasheet (§10 of the compendium).
5. **The dedicated Env Mod bias transistor (Q9) shifting the filter's DC operating point**, distinct from simply adding a CV term. The current implementation approximates this as an additive `cv_offset`/`cv_envmod` term in the same octave-CV sum as everything else, which gets the *qualitative* "small knob movement, big audible sweep" behavior in the right ballpark but doesn't model a literal bias-point shift interacting with the ladder's own nonlinear transfer curve.
6. **Resonance-dependent Accent Sweep time constant.** The real circuit's effective RC time constant for the accent-sweep capacitor varies continuously with the Resonance knob (via the 100 kΩ second-gang resistance) — the code uses one fixed 47 ms time constant for the capacitor regardless of Resonance, and instead expresses the Resonance/Accent-Sweep interaction entirely through a separate output-mixing weight (`resNorm * 0.7f` in `SynthEngine.cpp`). This is a reasonable approximation of the *result* but not the *mechanism*.
7. **Diode/transistor Vf asymmetry inside the filter.** The factory parts list includes at least one **germanium** diode (1S-188FM, Vf ≈ 0.3 V) alongside several **silicon** diode/transistor types (Vf ≈ 0.6 V), implying non-uniform forward-voltage behavior somewhere in the signal path. The filter's nonlinearity uses one uniform `Vt`/`tanh` shape for all four ladder stages, the new resonance-loop coupling-pole network, and the feedback path; no per-stage or per-junction Vf asymmetry is modeled. This would be cheap to add (a per-stage Vt multiplier) but there's no source for which stage(s) would use the germanium diode's lower Vf, so it's speculative rather than a known fix — flagged here as a "substantial guess" the user should treat with more skepticism than the coupling-pole frequency fix above.
8. **Most of the documented ≈6 further VCF coupling poles.** Only 1 sits inside the resonance feedback loop (150 Hz, see the Filter table above) plus 1 input-side and 1 output-side pole = 3 of ≈6. RobinSchmidt/Open303 gives a concrete template for the missing ones (a ~7.5 Hz notch, a ~14 Hz allpass, both outside the feedback loop) that hasn't been implemented yet — see "Biggest opportunities" above.
9. **Output/mixer coupling stage and stated output impedances** (10 kΩ line out, 8–30 Ω headphone out). Not relevant to a plugin's internal signal path, but worth noting as explicitly out of scope rather than accidentally omitted.
10. **Factory calibration-mode targets** (TM1–TM6 trim checkpoints, §11 of the compendium). There's no software "calibration mode" that could be validated against these checkpoints. (As of 2026-09, the plugin does expose a first set of hidden `vco_scale`/`filter_bias`-style calibration parameters — see the next section — but they're free-standing tuning knobs, not tied to the TM1–TM6 checkpoints specifically.)

## Performance note (2026-09 filter update)

All of the changes above are one-pole (or cascaded one-pole) linear filter stages evaluated once per oversampled tick inside `processFaithfulSample` — each costs roughly 2–4 FLOPs. At 8× oversampling and a typical host block/sample rate, this is immeasurably small next to the existing Newton-Raphson solve (3 iterations × a 4×4 tridiagonal solve, per oversampled tick) that already dominates the filter's cost. Since this is a monophonic synth (one filter instance active at a time, not one per voice in a polyphonic pool), there is substantial CPU headroom — none of the changes made here, nor the "cheap to extend further" follow-ups noted above (more coupling-pole stages, an Open303-style notch/allpass), are meaningful performance risks. The one change flagged above as **not** cheap is folding the coupling-pole network into the *implicit* Newton-Raphson solve itself (rather than treating it explicitly/pre-linearized, as done here) — that would enlarge the tridiagonal Jacobian to a pentadiagonal (or larger) system each Newton iteration, a real architectural change. It was deliberately not done: the coupling-pole's time constant (~1.1 ms at 150 Hz) is still large relative to one oversampled step (~2.8 μs at 8×/44.1kHz), so treating it explicitly costs negligible accuracy — there's no numerical-quality reason to pay for the implicit version.

## 2026-09-19: confirmed self-oscillation bug (fixed) -- resolved the render artifact too

A user-supplied render ("Faithful" mode, roughly Cutoff 0.28/Resonance 0.22/EnvMod 0.30/Decay 0.55/Accent 0.50, saw wave, a single held C2 note) showed a strong, spectrally **fixed** peak around 2650 Hz dominating the entire recording, regardless of the note played or its envelope — the classic signature of filter self-oscillation, not of a filtered sawtooth (whose loudest partial should be its own fundamental, or a resonance peak that tracks the cutoff/envelope). A same-settings Open303 render showed the expected, fundamental-dominated spectrum instead. Diagnosed with the new `tools/analyze_audio.py` (see below).

**Confirmed and fixed**: `src/filter_stability_test_main.cpp` (new; run it, see below) proved both `Filter::processAccurateSample` and `Filter::processFaithfulSample` **did self-oscillate** (failed to decay to silence after input stops) within the front panel's reachable 0.0–1.0 Resonance range — Accurate mode from Resonance≈0.6–0.8 depending on cutoff, Faithful mode from ≈0.7–1.0. This contradicted the "stock filter does not self-oscillate" research finding (`TB303_RESEARCH_COMPENDIUM.md` §6, Wikipedia's spec sheet). A subsequent detailed audit (`TB303_FILTER_AUDIT_2026-09-19.md`, supplied by the user from a parallel investigation) traced this to the exact root cause — feedback gain roughly 2x the ladder's analytically-derivable critical (self-oscillation) gain of 17 — which this session independently re-derived from scratch (the characteristic polynomial `s^4+8s^3+20s^2+16s+(2+2k)=0` and `k_critical=17` both confirmed by hand and numerically) and then implemented: see the Filter tables above for the specific fixes (feedback gain cap, resonance-knob skew, output-level compensation, capacitor-scale neutralization, cutoff-to-resonance-peak calibration). Post-fix, `syrebas_filter_stability_test` finds **zero self-oscillation across the entire 0.0–1.0 Resonance range at every tested cutoff**, in both modes.

**Resolved**: this fix eliminated the ~2650 Hz render artifact too, confirmed by the user re-testing. The reproduction attempts noted above (which couldn't trigger it from the read-off-the-screenshot knob settings) simply hadn't hit the right combination of cutoff/resonance to cross the pre-fix instability boundary in this project's own test harness — the fix itself, being a genuine correction of a real bug rather than a guess targeted at one file, covered the actual cause regardless.

**Follow-up (same day): knob-range mismatch.** After the self-oscillation fix, the user compared this project against an Open303-based reference (JC-303) at matching settings and found the two sounded close, but only when *this* project's Resonance and Env Mod knobs were maxed out where the reference needed only about half its travel for a similar effect — Cutoff matched fine. Diagnosed and fixed:
- **Resonance**: the self-oscillation fix's flat 15.3 ceiling, while safe everywhere, was far too conservative — it left almost all of the coupling-pole HPF's real stability headroom unused, so the resonant peak only reached ~2.5 dB above passband even at Resonance=1.0 (cutoff=2500 Hz). Empirically re-measured the *actual* per-cutoff stability boundary (bisection search against the real `Filter` class) and added `kCutoffHeadroomNumerator_` to reclaim it safely — see the Faithful-mode filter table above. Re-verified with `syrebas_filter_stability_test` (now sweeping 100 Hz–15 kHz): still zero self-oscillation everywhere, with the resonant peak now roughly doubled (~5 dB) at the same test point.
- **Env Mod**: was mapped through a squared ("quadratic audio taper") curve with no real justification. Open303's own measured Env Mod calibration (`calculateEnvModScalerAndOffset()`, its own comment: "arise from the measurements") is linear, not quadratic. Switched to linear — see the SynthEngine table above.

Both fixes were validated for stability (`syrebas_filter_stability_test`, `stress_test.cpp`-style parameter-extreme sweeps) before being reported back; neither has yet been re-validated by ear against the Open303 comparison at the *new* knob ranges, since only the user can do that.

New tooling committed alongside this investigation:
- `tools/analyze_audio.py` — reusable WAV spectral diagnostic (band-energy breakdown, fundamental-vs-overall-peak comparison, an explicit self-oscillation warning when the strongest peak doesn't track the fundamental across time). Works on any 16/24-bit PCM WAV, no dependencies. Intended for future render-vs-reference comparisons, including against real hardware recordings once isolated single-note/known-knob-position samples are available.
- `src/filter_stability_test_main.cpp` (build target `syrebas_filter_stability_test`) — sweeps cutoff × resonance for both filter modes and reports the self-oscillation boundary. Run this after any change to `Filter.cpp`'s feedback gain, coupling-pole, or capacitor-scale constants as a permanent regression check.
